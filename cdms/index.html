CRScube CDMS 가 API 게이트웨이를 통해 외부에 노출하는 REST API 명세입니다.

CDMS 연동에 사용하는 외부 공개 API 를 정리한 문서입니다.

상태 코드를 읽는 법

HTTP 상태 코드가 통념과 다르게 쓰이는 지점이 여러 곳 있습니다. 연동 전에 반드시 확인하세요.

상황 실제 응답 통념
CRF 서버 측 처리 실패 200 + result: false 5xx
CRF 과제 접근 권한 없음 200 + (2200) 403
추출 작업 진행 중 / 다운로드 미완료 202 + status: fail 409
리소스 없음 (RESOURCE_NOT_FOUND) 400 404
권한 없음 (FORBIDDEN) 400 403
dataset 내부 오류 (INTERNAL_SERVER_ERROR) 400 500
Central Lab FileKey 없음 401 404
Central Lab 데이터 버퍼 초과 413 400
스크리닝 번호 중복 (CONFLICT) 409 409

2xx 를 성공으로 단정하지 마세요. 200·202 에 실패가 실려 옵니다.

401·403·404·500·504 는 게이트웨이가 반환합니다. CRF 엔드포인트만 이 오류도 ApiResponse 형식으로 전달하고, 나머지는 GatewayFailResponse 형식을 씁니다.

응답 형식

응답 형식 구조 사용처
ApiResponse {txId, result, error{message, errors}} CRF, CRF 의 게이트웨이 오류
SuccessResponse / FailResponse {status, result} / {status, message, error{errorCode, errorDetails}} dataset GET
ExternalSuccessResponse / ExternalFailResponse 위 + txId dataset POST, subject
GatewayFailResponse {txId, error{errorCode, errorDetails}, message, status} 게이트웨이 공통 오류
CentralLabFailResponse 위와 같은 형태, errorCode 집합이 다름 central-lab

crf

외부 EDC 벤더의 CRF 데이터 업로드.

CRF 데이터 업로드

외부 시스템이 수집한 CRF 항목을 대상자에게 저장합니다.

처리는 작업 생성 → CRF 데이터 적재 → 업로드 실행 순으로 진행되며, 각 단계의 실패가 서로 다른 GatewayError 로 분류됩니다.

서버 측 처리 실패는 HTTP 200 으로 응답하고 본문의 result 가 false 입니다.

실패 지점 GatewayError HTTP
작업 초기화 실패 SERVER_INITIALIZATION_FAILED 200
CRF 데이터 검증 실패 SERVER_VALIDATION_FAILED 200
저장 실패 SERVER_SAVE_FAILED 200
데이터 처리 오류 SERVER_PROCESSING_FAILED 200

HTTP 상태만으로 성패를 판단하지 마세요.

데이터셋 추출 작업 생성

비동기 추출 작업을 생성하고 작업 키를 반환합니다. 진행 상태는 GET .../dataset/jobs/{jobKey} 로 조회하고, 완료 후 /download 로 내려받습니다.

검증 순서는 다음과 같으며, 각 단계 실패가 서로 다른 errorCode 로 나타납니다.

  1. 사용 권한 확인 — RESOURCE_NOT_FOUND / FORBIDDEN (400)
  2. codeType·fileType 파싱 — RESOURCE_NOT_FOUND (400)
  3. 도메인 존재 확인 — RESOURCE_NOT_FOUND (400)
  4. NonCRF(Audit trail) 혼합 여부 — INVALID_REQUEST (400)
  5. codeType × fileType 조합 — INVALID_REQUEST (400)
  6. 진행 중 작업 확인 — UNABLE_OPERATE_STATUS (202)

subject

외부 시스템의 시험대상자 등록.

시험대상자 등록 (외부 시스템용)

외부 시스템이 시험대상자를 등록합니다. 요청의 txId 가 성공·실패 응답에 그대로 실려 오므로 호출 측에서 트랜잭션을 추적할 수 있습니다.

  1. 팀 존재 확인 — 없으면 RESOURCE_NOT_FOUND (400, 404 아님)
  2. 스크리닝 번호 중복 확인 — 중복이면 CONFLICT (409)

studyId 는 대소문자를 구분하지 않습니다.
