How to read the status codes

There are several places where HTTP status codes are used differently from what you would expect. Review this table before you integrate.

Situation Actual response Expected
CRF server-side processing failure 200 + result: false 5xx
No study access permission for CRF 200 + (2200) 403
Extraction in progress / download not ready 202 + status: fail 409
Resource not found (RESOURCE_NOT_FOUND) 400 404
No permission (FORBIDDEN) 400 403
Internal dataset error (INTERNAL_SERVER_ERROR) 400 500
Central Lab FileKey missing 401 404
Central Lab data buffer exceeded 413 400
Duplicate screening number (CONFLICT) 409 409

Never treat 2xx as success on its own. Failures arrive with 200 and 202.

401, 403, 404, 500 and 504 are returned by the gateway. Only the CRF endpoint delivers those errors in the ApiResponse format; everything else uses GatewayFailResponse.

Authentication

HTTP Basic Authentication (RFC 7617), verified by the gateway.

This API is stateless. There is no login or session step, so every request must carry its credentials in the header.

Authorization: Basic {base64(clientId:clientSecret)}

Join the clientId and password issued to you with : and Base64-encode the result (RFC 7235 4.2). Most HTTP clients build this for you (curl -u and the like). To build it yourself:

// Apache Commons Codec
final String clientId = "clientId";
final String clientPassword = "clientPassword";
return new HttpHeaders() {{
    String auth = clientId + ":" + clientPassword;
    byte[] encodedAuth = Base64.encodeBase64(auth.getBytes(Charset.forName("US-ASCII")));
    String authHeader = "Basic " + new String(encodedAuth);
    set("Authorization", authHeader);
}};

// Base64Utils - removed in Spring Framework 6. Prefer the approach below.
final String clientId = "clientId";
final String clientPassword = "clientPassword";
return new HttpHeaders() {{
    String auth = clientId + ":" + clientPassword;
    String authHeader = "Basic " + Base64Utils.encodeToString(auth.getBytes(StandardCharsets.US_ASCII));
    set("Authorization", authHeader);
}};

// java.util.Base64 - no extra dependency required.
String auth = clientId + ":" + clientPassword;
String authHeader = "Basic " + Base64.getEncoder()
        .encodeToString(auth.getBytes(StandardCharsets.US_ASCII));

import base64
auth = base64.b64encode(f"{client_id}:{client_password}".encode("ascii")).decode()
headers = {"Authorization": f"Basic {auth}"}
Caution Detail
Credential characters Use ASCII only. A charset mismatch between encoding and decoding returns 401
No line breaks MIME-style encoders wrap every 76 characters and corrupt the header value
Every request There is no session to authenticate once and reuse

Query string encoding

Encode parameters before sending them, but encode them only once. Passing an already-encoded string back through a URI template turns %40 into %2540, and the value stops matching.

Rest Template and WebClient re-parse and re-encode a URL passed as a string, treating it as a URI template. Pass a URI, not a string.

// Building the URI directly
String url = "https://api.example.com/";
Map<String, String> params = new HashMap<>();
params.put("userEmail", "test\"?=!@example.com");

String requestUri = params.entrySet().stream()
                          .map(it -> it.getKey() + "=" + URLEncoder.encode(it.getValue(), StandardCharsets.UTF_8.name()))
                          .collect(Collectors.joining("&", url + "?", ""));

URI uri = URI.create(requestUri);

A + inside a value must be encoded as %2B. In a query string + means a space, and RFC 3986 encoders may leave it as is, so user+tag@example.com arrives as user tag@example.com.

// Building it with UriComponentsBuilder - replace "+" with "%2B".
String url = "https://api.example.com/";
Map<String, String> params = new HashMap<>();
params.put("userEmail", "test\"?=!@example.com");

final UriBuilder builder = (new DefaultUriBuilderFactory()).uriString(url);
for (Map.Entry<String, String> entry : params.entrySet()) {
    builder.queryParam(entry.getKey(), entry.getValue());
}
final URI temporal = builder.build();
final URI uri = UriComponentsBuilder.fromUri(temporal)
                                    .replaceQuery(temporal.getRawQuery().replace("+", "%2B"))
                                    .build(true)
                                    .toUri();

build(true) marks the value as already encoded. Drop it and it gets encoded again.

This applies to userId (an email address) and fileKey.

Symptom Cause
200 with an empty result The value was encoded twice
Text after + in an email became a space + was not encoded as %2B

Generating txId

The unique identifier tying one transaction together from request to response. The client generates it as a UUID version 1 and sends it. 36 bytes max.

import uuid
tx_id = str(uuid.uuid1())

import { v1 as uuidv1 } from "uuid";
const txId = uuidv1();

The JDK has no version 1 generator (randomUUID is version 4). Build one yourself or use a library.

// Reference: https://www.baeldung.com/java-uuid
public static void printUUID() {
    System.out.println("UUID:" + generateType1UUID().toString());
}

private static UUID generateType1UUID() {
    long most64SigBits = get64MostSignificantBitsForVersion1();
    long least64SigBits = get64LeastSignificantBitsForVersion1();

    return new UUID(most64SigBits, least64SigBits);
}

private static long get64LeastSignificantBitsForVersion1() {
    Random random = new Random();
    long random63BitLong = random.nextLong() & 0x3FFFFFFFFFFFFFFFL;
    long variant3BitFlag = 0x8000000000000000L;
    return random63BitLong + variant3BitFlag;
}

private static long get64MostSignificantBitsForVersion1() {
    LocalDateTime start = LocalDateTime.of(1582, 10, 15, 0, 0, 0);
    Duration duration = Duration.between(start, LocalDateTime.now());
    long seconds = duration.getSeconds();
    long nanos = duration.getNano();
    long timeForUuidIn100Nanos = seconds * 10000000 + nanos * 100;   // see below
    long least12SignificatBitOfTime = (timeForUuidIn100Nanos & 0x000000000000FFFFL) >> 4;
    long version = 1 << 12;
    return (timeForUuidIn100Nanos & 0xFFFFFFFFFFFF0000L) + version + least12SignificatBitOfTime;
}
  • nanos * 100 should be nanos / 100, because the time field is measured in 100-nanosecond units. Uniqueness comes from the low 63 random bits, so this does not break anything in practice, but the embedded timestamp is off and is not monotonic.
  • It is not a deduplication key. Sending the same txId again is not rejected, so retrying a write applies it twice.
  • Do not sort by it. The timestamp is not monotonic, for the reason above.

crf

CRF data upload from external EDC vendors.

Upload CRF data

Stores CRF items collected by an external system against a subject.

Processing runs as job creation → CRF data staging → upload execution, and a failure at each stage maps to a different GatewayError.

Server-side processing failures return HTTP 200 with result set to false in the body.

Failure point GatewayError HTTP
Job initialization failed SERVER_INITIALIZATION_FAILED 200
CRF data validation failed SERVER_VALIDATION_FAILED 200
Save failed SERVER_SAVE_FAILED 200
Data processing error SERVER_PROCESSING_FAILED 200

Do not judge success or failure from the HTTP status alone.

Create a dataset extraction job

Creates an asynchronous extraction job and returns its job key. Poll progress with GET .../dataset/jobs/{jobKey}, then download the result from /download once it completes.

Validation runs in the following order, and each stage fails with a different errorCode.

  1. Usage permission — RESOURCE_NOT_FOUND / FORBIDDEN (400)
  2. codeType and fileType parsing — RESOURCE_NOT_FOUND (400)
  3. Domain existence — RESOURCE_NOT_FOUND (400)
  4. NonCRF (Audit trail) mixed with other sources — INVALID_REQUEST (400)
  5. codeType x fileType combination — INVALID_REQUEST (400)
  6. Job already in progress — UNABLE_OPERATE_STATUS (202)

Download the extraction result file

Streams the output file of a completed extraction job.

When a download is possible

The job status must be Success or Fail. Calling this endpoint while the status is Initialization, Progress or Continue returns HTTP 202 with UNABLE_OPERATE_STATUS. That is a 2xx, but it is a failure.

Even when the status qualifies, a missing output file returns RESOURCE_NOT_FOUND (400).

Content-Type is derived from the file extension.

studyId is case-insensitive.

central-lab

Central Lab test data upload and lookup.

The response format and error-code scheme differ from the other areas. Status codes are used differently too: a missing FileKey returns 401, and exceeding the data buffer returns 413.

Upload Central Lab data

Sends lab test results as JSON. The job ID (fileKey) is returned immediately and processing continues asynchronously.

Poll progress with GET /central-labs/{fileKey}.

Differences between v1 and v2

Item v1 v2
txId optional required
Error response carried in result carried in error

This specification describes v2.

The data items you can send depend on the BUILDER > DCL > Central Lab configuration. Use the ID of each configured item as the JSON key; items that are not configured may be omitted.

Look up validation result details

Returns per-row success and failure details of the validation performed on uploaded raw data. Use the result parameter to select only successful (S) or only failed (F) rows.

For failed rows, the reason is carried in MESSAGE (for example, "This subject doesn't exist. [Screening No.]").

A large result set triggers 413, so lower rowCount and call again.
